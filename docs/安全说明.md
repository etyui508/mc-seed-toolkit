# 安全说明

自动更新是整套工具里唯一"会自己下载东西并覆盖到本地"的功能，所以它是安全上的重点。
这份文档说清楚：**我们防住了什么、怎么防的、还剩什么需要你在后台手动开。**

---

## 一、三层防线

```
① HTTPS（TLS）          防路上被人偷看 / 顺手改包
② 清单 Ed25519 签名      防线里的主心骨：域名/服务器被黑也推不出能用的包
③ 包的 sha256 校验       防下载不完整、防换包
```

### 为什么光有 HTTPS 不够

HTTPS 只保证"你连的那台服务器确实是 `mcdownload.bony-doorframe-shortly.top`"
（走主站时是 `github.com` —— 多一个来源，可靠性更高，代价是"被劫持的面"也多一个，
所以这两个来源拿到的清单一律要过同一套签名校验；备用地址本身也必须在白名单里，
不然清单里写个外部地址就能把用户导走）。
但如果**域名被劫持**、**Cloudflare 账号被盗**、**服务器被拿下**，
攻击者可以合法地拿到证书、合法地给你返回恶意内容 —— 他甚至能算出"正确的" sha256。
这时候只有**签名**救得了你。

### 签名是怎么做的

- 发布机（这台机器）上有一把**私钥**：`~/.mc-keys/mc-seed-toolkit.key`（权限 0600）
- 客户端里内置**公钥**：`app/release.py` 的 `PUBLIC_KEYS`
- 每次发布，`publish.sh` 都会对清单签名；清单里存的是 `sig`
- 客户端拿到清单一律先验签：**签名不对就不下载、不解压、不替换**

私钥**不在网站目录里**。所以"网站被黑"最多让别人拿到公钥和已发布的包
——他既没法伪造新版本，也没法改现有版本（改一个字节签名就废）。

客户端会拒绝这些情况：

| 情况 | 结果 |
| --- | --- |
| 清单没有签名 / 签名不对 | ❌ 拒绝更新，并大声警告"下载站可能被动了手脚" |
| 清单被改过（版本号、sha256、下载地址任意一处） | ❌ 同上 |
| 下载地址不是 https | ❌ 拒绝 |
| 下载地址不是我们认可的域名 | ❌ 拒绝 |
| 包大小 / sha256 和清单对不上 | ❌ 拒绝 |
| 线上版本比本地**旧**（重放旧包） | ❌ 不降级 |
| 关键文件（`app/` 下的代码）没换成功 | ❌ 不记新版本号，下次启动自动重试 |

> 调试用：`MC_UPDATE_ALLOW_UNSIGNED=1` 可以跳过验签（**只有自己在调的时候该用**）。

## 二、下载服务器做了什么

`~/mc-download/serve.py`，通过 Cloudflare 隧道对外，只绑 `127.0.0.1:8477`：

- **只放行三类文件**：`manifest.json`、`mc-seed-toolkit-*.zip`、`*.sha256`
- **不列目录**（默认的 SimpleHTTPRequestHandler 会列，已经关掉）
- 以 `.` 开头的文件一律不服务
- 路径穿越（`../`、`..%2f`）一律 404
- 加了 `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`

发布脚本 `publish.sh`、服务脚本 `serve.py`、说明文档**都不对外**，
私钥更是根本不在这台网站的目录里。

## 三、还得你在后台点几下的（我做不了）

隧道的授权证书只能管 DNS 记录和隧道，改不了这些设置。按重要性排：

### 1. 开 DNSSEC（防 DNS 劫持）⭐

现状：**没开**（查 `DS bony-doorframe-shortly.top` 是空的，响应里也没有 RRSIG）。

1. Cloudflare 后台 → 选 `bony-doorframe-shortly.top` → **DNS → Settings → DNSSEC → Enable**
2. 它会给你一条 **DS 记录**，复制下来
3. 去**域名注册商**后台，找到 DNSSEC / DS 记录的地方，把那条贴进去
4. 等生效后回来验证：`dig +short DS bony-doorframe-shortly.top @223.5.5.5` 有输出就对了

> 注意：DNSSEC 只在**解析器做校验**的时候起作用，国内有些公共 DNS 不校验。
> 所以它是"多一层"，真正兜底的是签名。

### 2. 注册商那边上锁（防域名被转走）

- **域名锁定**（Registrar Lock / clientTransferProhibited）→ 打开
- 注册商账号开 **两步验证**
- 注册邮箱也开两步验证（域名转移动静是发邮件确认的）

### 3. Cloudflare 账号开两步验证

Cloudflare 账号一旦丢了，别人可以改隧道、改 DNS。后台 → My Profile → Authentication → Two-Factor。
顺便把能登录的 API Token 都看一遍，不用的删掉。

### 4. 加一条 CAA 记录（防止别人拿你的域名去签证书）

现状：**没有 CAA 记录**。加上之后，只有你指定的 CA 能给这个域名签证书，
能挡掉一部分"伪造证书搞中间人"的路子。

Cloudflare → DNS → 加记录：

```
类型: CAA    名称: @    标志: 0    标签: issue    值: pki.goog; cansignhttpexamples.com
```

（`pki.goog` 是 Google Trust Services，Cloudflare 免费证书常用它；也可以换成
`letsencrypt.org`。具体用哪家可以在 Cloudflare 的 SSL/TLS → Edge Certificates 里看到。）

## 四、私钥怎么保管

**丢了会怎样**：以后再也签不出客户端认的包 —— 只能发一个"内置了新公钥"的新版本，
让所有人手动更新一次。所以：

1. 把 `~/.mc-keys/mc-seed-toolkit.key` 抄一份到**离线**的地方（U 盘 / 密码管理器 / 打印出来）
2. 别放进网站目录，别提交到 git，别丢聊天记录里
3. 这台机器重装系统前，**先备份它**

**想换钥匙**：`tools/sign-release.py --genkey` 会把新公钥写进 `app/release.py` 的
`PUBLIC_KEYS`（**是追加，不是替换**）。所以旧客户端既认旧公钥也认新公钥，
发一版新版本之后，所有人就都拿到新公钥了，再考虑移除旧的。

---

## 五、出事了怎么办

**如果你怀疑下载站被黑了**：

1. 别慌，用户那边**已经自动拒绝**了（签名对不上），不会有人的电脑装上后门
2. 看客户端报的是什么：`签名对不上` = 内容被改过；`连不上` = 只是网络问题
3. 检查服务器上的 `manifest.json` 是不是你签的那个：

   ```bash
   cd ~/mc-seed-toolkit && python3 tools/sign-release.py --verify ~/mc-download/manifest.json
   ```

4. 重新签名发布：`cd ~/mc-download && bash publish.sh "重新发布"`
5. 改 Cloudflare / 注册商密码，开两步验证，检查有没有陌生的 DNS 记录

**如果你把私钥弄丢了**：发一个内置新公钥的新版本（见上一节），
让大家手动下载一次 —— 自动更新这条路对新公钥是通的（因为客户端只认清单签名，
而清单这时是用新钥匙签的，客户端里的 `PUBLIC_KEYS` 已经更新过了）。

## 六、还剩什么防不住

老实说清楚，免得有虚假的安全感：

- **发布机（这台电脑）被完全控制** → 攻击者能直接用私钥签恶意包。所以这台机器的密码、SSH、Cloudflare 登录都要保护好。
- **用户本地被投毒**（比如有人手动把 `app/release.py` 里的公钥改了）→ 签名就形同虚设。这也是为什么更新时**不动** `app/release.py` 以外的信任根……实际上我们会更新它，所以本地已经被拿下的话，什么都防不住。
- **拒绝服务**：攻击者可以让你连不上下载站（换不了包，但推不了恶意包）。
- **首次下载**：第一次拿到这个包的时候，没有任何"信任根"可比对，只能靠你从可信渠道获取。
